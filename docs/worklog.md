# 작업 기록

날짜별로 무엇을 했는지, 왜 했는지, 결과가 어땠는지 기록합니다. 원인 분석은 [troubleshooting](troubleshooting.md), 수치의 원자료는 [benchmarks](benchmarks/)에 있습니다.

## 2025-04-06 – 04-07 · 원본 구현 (`67cd50e` – `c8d7002`)

- Django + Channels + WebRTC로 랜덤 1:1 화상 대화를 처음 구현했습니다. HTTP 뷰가 SQL의 `Room.user_count`를 보고 방 번호를 고르고, WebSocket이 방 그룹에 신호를 뿌리는 구조였습니다.
- 개발하면서 직접 해결한 문제 10가지는 [history/original-troubleshooting.txt](history/original-troubleshooting.txt)에 남아 있습니다. 가상환경, 로컬 DB, 개발용 비밀키가 저장소에 함께 올라가 있었습니다.

## 2026-10-21 – 10-24 · 안정화 재구축 (`714db72`)

- **원인**: 원본은 동시 접속에서 정원 초과, 유령 방, 신호 혼선이 생겼습니다. 운영용 ASGI 서버(Daphne)로는 시작조차 되지 않았습니다.
- **변경**
  - 매칭을 Redis Lua 하나로 원자화했습니다. 신호에는 match_id 범위 제한과 입력 검증을 넣었습니다.
  - heartbeat와 presence TTL로 자동 정리하고, 재연결과 TURN 자격증명 갱신을 추가했습니다.
  - 가상환경·DB·키를 추적 대상에서 빼고 `backend/`로 옮겼습니다.
- **검증**: 서버 테스트 13개, Playwright e2e(실제 브라우저 간 WebRTC), GitHub Actions 설정.

## 2026-10-25 오전 · 측정, 성능, 운영 기능 (`c6635a0`, `48b7853`, `b132a39`)

- **부하 도구 작성**(`loadtest/matching.py`): 실제 WebSocket 클라이언트로 매칭 정확도와 지연을 측정합니다. 원본도 git에서 꺼내 같은 도구로 측정했습니다.
  - 원본: 200명/5초에서 정상 매칭 3–22%
  - 현재: 100%
- **측정으로 찾은 병목**
  - WebSocket마다 Redis 연결 풀이 생기던 문제를 공유 풀로 바꿔, 200명 기준 Redis 연결이 212개에서 17개로 줄었습니다(T6).
  - 메시지 중계 때 매칭 상태를 다시 조회하지 않게 해서, 메시지 1개당 Redis 명령이 26개에서 10개로 줄었습니다(T8).
- **측정 도구의 버그**를 찾아 고쳤습니다(T7). 메시지를 보낸 쪽이 먼저 소켓을 닫아 생긴 가짜 실패였습니다.
- **운영 기능**
  - IP별 연결 제한, 로그인·가입·RTC 설정 요청 제한
  - 신고/차단/자동 제한
  - `/metrics/`
  - 같은 IP 게스트끼리 신고하면 IP 전체가 막히는 버그를 발견해 수정했습니다(T9).
  - 직전 상대 제외가 사라지는 기존 버그도 발견해 수정했습니다(T10).
- **문서**: README를 문제→측정→해결 순서로 다시 쓰고, 트러블슈팅·운영·배포 문서를 추가했습니다.

## 2026-10-25 오후 · CI 확장, Linux 측정, main 병합 (`5f168e2` – `e0aaf87`)

- **레거시 계정 정리**: CustomUser 계정을 비밀번호 해시째 auth.User로 옮기는 마이그레이션을 만들었습니다. 로컬 DB 복사본으로 검증했습니다.
- **CI 추가**: 운영 Docker 이미지로 실제 매칭 200건, Chromium↔Firefox 상호 운용, Linux 부하 측정을 CI에 넣었습니다.
- **Linux 측정에서 새 병목 발견**(T11): 한 프로세스에 1,000명이 동시에 몰리면 정상 매칭이 4.6–43%였습니다. 원인은 channels_redis 수신함 초과로 인한 매칭 알림 유실이었습니다.
  - 로컬에서 같은 증상을 재현한 뒤 수정했습니다(재시도 backoff, 매칭 되돌리기, 기본 용량 상향). 결과는 100%였습니다.
  - main 병합 후 스트레스 조건이 98%로 떨어진 것을 보고 "되돌린 두 사람이 영원히 대기"하는 문제를 한 번 더 고쳤습니다.
- **잘못된 카메라 오류 안내 수정**(T12).
- `codex/reliable-videochat`을 main에 병합했습니다(`cb9174d`).

## 2026-10-25 저녁 · 끊김 복구, 선호 매칭, 신고 근거, 대시보드

**고치기 전에 먼저 측정했습니다.** 통화 중 장애를 일으켜 같은 상대와 대화가 이어지는지 세는 테스트(`tests/resilience.cjs`)를 만들었습니다. 이전 커밋은 별도 worktree로 띄워 같은 조건에서 비교했습니다.

| 작업 | 이유 | 결과 |
| --- | --- | --- |
| 통화 재개(suspend/resume) | 신호 연결이 잠깐 끊겨도 대화가 끝남 | 같은 상대와 대화 유지 0/20 → **20/20**, 중앙값 1.1초 |
| ICE restart | 미디어 경로가 끊기면 즉시 종료 | 0/20 → **20/20**, 중앙값 0.6초(상태 이벤트 주입으로 검증) |
| 통화 품질 지표 | 매칭 성공과 통화 성공을 구분할 수 없었음 | 연결 성공/실패, 연결 시간, TURN 경유, 복구 결과를 매칭당 1회 집계 |
| 언어·관심사 선호 매칭 | 대화 소재가 될 공통점 | 공통 관심사 매칭 40–46% → **99–100%**, 대기 p95 +0.3초(초당 10명). "기다리지 않는 최선" 방식은 효과가 없음을 측정으로 확인 |
| 신고 근거 | 관리자가 사유만 보고 판단해야 했음 | 서버가 중계한 최근 대화 20줄을 신고 시에만 저장 |
| Grafana 대시보드·경보 규칙 | 지표는 있었지만 볼 화면이 없었음 | compose `monitoring` profile, CI에서 수집·등록 검증 |

이 과정에서 찾은 문제:
- 같은 IP 사용자가 많으면 RTC 설정 한도에 걸려 정상 사용자도 연결에 실패하고 안내도 틀렸습니다(T13).
- 공통 관심사 표시가 상대의 마이크 상태 메시지에 덮어써졌습니다(T14).
- `1 == True` 때문에 잘못된 신호가 검증을 통과했습니다(T15).
- 측정 스크립트가 재사용된 PID로 Redis를 종료했습니다(T16).

Lua가 후보를 모두 검사하게 바뀌면서 생길 수 있는 성능 회귀는 "최고 점수면 탐색 종료"로 막았습니다. 부하 측정에서 1개·4개 프로세스 모두 100%와 이전 수준의 지연을 확인했습니다.

## 2026-10-25 밤 · 독립 코드 리뷰와 유사 서비스 조사

- **독립 코드 리뷰**: 구현에 참여하지 않은 리뷰어에게 코드를 처음 읽게 했습니다. 15건이 보고됐고, 모두 코드와 대조해 확인한 뒤 수정했습니다([code-review](code-review.md)).
  - 사용자 피해가 큰 결함: 신고 다이얼로그를 여는 사이 새 상대가 매칭되면 **새 상대가 신고됨**, 드문 경쟁 상황에서 "찾는 중" 화면에 무기한 멈춤, 선호 매칭이 조건에 맞는 상대보다 완화된 상대를 먼저 고름, 관리자 로그인에 제한이 없음.
  - 핵심 4건은 수정 전 코드에서 테스트가 실패하는 것까지 확인했습니다. 신고 경쟁 상황은 브라우저 3개로 재현하는 e2e를 추가했습니다.
  - 그 밖의 조치: 신고 대화 90일 보관 후 삭제, 상대에게 IP를 숨기는 TURN 전용 옵션, debug 기본값 끄기, 접근성(항상 들리는 상태 안내, 포커스 관리).
- **유사 서비스 조사**: Azar, OmeTV, Chatroulette, Monkey, Emerald Chat, Uhmegle와 국내외 규제를 비교했습니다([competitive-analysis](competitive-analysis.md)).
  - 가장 큰 차이는 안전 장치입니다. 연령 확인, 연결 직후 영상 가림, 사람의 신고 검토, 계정 단위 제재가 없습니다.
  - 국내에서는 2020년 여성가족부 고시(본인인증·대화 저장·신고 기능 중 하나라도 없으면 청소년유해매체물)가 지금도 목록에 있어, 그대로 공개 운영하면 지정 대상입니다.
- **정리**: 쓰이지 않던 원본 템플릿과 정적 파일(Bootstrap 페이지, jQuery 스크립트, 이미지)을 삭제했습니다.
