# 매칭 부하 측정

측정일: 2026-10-25 · 원자료: [results.jsonl](results.jsonl) (실행 1회 = 1줄)

## 무엇을 재는가

실제 WebSocket 클라이언트 N명이 동시에 접속해 매칭을 요청합니다. 각 실행에서 다음을 기록합니다.

| 지표 | 의미 |
| --- | --- |
| 정상 매칭 비율 | 같은 match_id(원본은 같은 방 번호)를 **정확히 2명**이 공유한 비율 |
| 방 크기 분포 | 1명(혼자 대기), 2명(정상), 3명 이상(정원 초과) |
| join→matched | 대기 중인 상대를 찾은 쪽의 지연. 서버 처리 시간만 포함 |
| 대기열 대기 | 먼저 와서 기다린 쪽의 지연. 다음 사람이 도착할 때까지의 시간 포함 |
| 채팅 중계 | 한쪽이 보낸 메시지가 상대 브라우저에 도착하기까지 (같은 프로세스 시계로 측정) |
| 실패 | 단계별(connect/match/chat) 예외 수, HTTP 5xx |

## 환경

- Windows 11, Intel Core Ultra 5 225H(논리 14코어), RAM 15.4 GB. 노트북 한 대에서 클라이언트, 서버, Redis를 함께 실행
- Python 3.12.14, Daphne 4.1.2, Channels 4.2.0, channels_redis 4.2.1, Redis 5.0.14
- 서버는 운영과 같은 Daphne ASGI 프로세스. 프로세스가 여러 개면 클라이언트를 라운드로빈으로 나눠 붙여 **프로세스를 넘나드는 매칭**까지 검증
- Windows의 Daphne(Twisted asyncio reactor)는 `select()`를 써서 FD가 512개로 제한됩니다. 그래서 프로세스당 250명 이하로 측정했습니다. Linux 운영 환경(epoll)에는 없는 제약입니다.

## 결과 1 — 원본 구현 대비 매칭 정확도

원본(`c8d7002`)을 git에서 그대로 꺼내 같은 도구로 측정했습니다. 원본 흐름은 `GET /chat/start_chat/` → 방 번호로 리디렉션 → `/ws/chat/<방>/` 접속입니다.
실행마다 서버와 Room 테이블을 새로 만들었고, 각 조건을 3회 반복했습니다.

| 조건 | 원본: 정상 매칭 | 원본: 최대 방 인원 | 원본: HTTP 500 | 원본: 종료 후 유령 방 | **현재: 정상 매칭** |
| --- | --- | --- | --- | --- | --- |
| 200명 / 5초 분산 | 3 – 22% | 10 – 15명 | 2 – 6건 | 27 – 56개 | **100% (3/3회)** |
| 200명 / 동시 | 4 – 11% | 8 – 9명 | 6 – 9건 | 41 – 42개 | **100% (3/3회)** |
| 800명 / 동시, 4개 프로세스 | — | — | — | — | **100% (3/3회)** |
| 1,000명 / 10초, 4개 프로세스 | — | — | — | — | **100% (3/3회)** |

유령 방이 이후 사용자에게 미치는 영향도 따로 측정했습니다. 20명이 대화를 마친 뒤 Room 테이블을 초기화하지 않고 다음 20명을 받으면, 원본은 **50 – 60%만 매칭**되고 나머지는 아무도 없는 방에 혼자 남았습니다(3회).

원인은 [트러블슈팅 T1–T4](../troubleshooting.md)에 정리했습니다.

## 결과 2 — 현재 구현의 지연 (3회 중앙값, ms)

| 조건 | join→matched p50 / p95 | 채팅 중계 p50 / p95 | 대기열 대기 p95 | 실패 |
| --- | --- | --- | --- | --- |
| 1 프로세스, 200명 / 5초 분산 | 2.9 / 5.5 | 2.4 / 5.6 | 91 | 0 |
| 4 프로세스, 1,000명 / 10초 분산 | 2.5 / 4.6 | 2.5 / 4.7 | 52 | 0 |
| 1 프로세스, 200명 동시 접속 | 82 / 113 | 148 / 181 | 308 | 0 |
| 4 프로세스, 800명 동시 접속 | 113 / 169 | 177 / 222 | 403 | 0 |

`with-moderation` 레이블(신고·제한·지표 기능을 모두 넣은 최종 코드) 기준입니다.
동시 접속 조건의 지연은 대부분 WebSocket 핸드셰이크 처리 대기열에서 생깁니다.

**같은 노트북에서 측정한 지연은 실행 묶음마다 편차가 큽니다.** 개선을 하나씩 적용하며 측정한 세 묶음(`shared-pool` → `local-relay` → `with-moderation`)에서 동시 접속 조건의 join→matched p50은 82 – 297ms 사이에서 움직였고, 기능이 가장 많은 마지막 묶음이 오히려 가장 빨랐습니다. 그래서 아래 최적화의 효과는 지연 대신 **결정적으로 셀 수 있는 지표**(연결 수, 명령 수)로 판단했습니다.

## 결과 3 — 측정으로 찾은 병목과 개선

| 문제 | 측정 | 개선 후 |
| --- | --- | --- |
| WebSocket마다 Redis 연결 풀 생성 | 접속 200명일 때 Redis 연결 **212개** (`INFO clients`), 프로세스당 약 250명에서 FD 한계로 서버 종료 | 이벤트 루프당 상한 50의 공유 풀: **17개** |
| 메시지 중계마다 양쪽에서 매칭 상태 조회 | 채팅 1개당 Redis 명령 **26개** (Lua 2회 포함, `INFO commandstats`) | 매칭 확정 시 검증한 상대/ID를 로컬에 보관: **10개**(-62%), Lua **0회** |

SDP/ICE 시그널도 같은 중계 경로를 쓰므로 통화 연결 한 번에 오가는 수십 개 메시지가 모두 영향을 받습니다.
자세한 경위는 [트러블슈팅 T6, T8](../troubleshooting.md)에 있습니다.

## 결과 4 — Linux CI 측정

Windows의 `select()` 한계 때문에 프로세스당 1,000명 이상은 GitHub Actions `ubuntu-latest` 표준 러너에서 측정했습니다([loadtest.yml](../../.github/workflows/loadtest.yml), [bench.sh](../../loadtest/bench.sh)). 클라이언트, 서버, Redis가 한 러너에 함께 있습니다. 결과는 실행 페이지의 annotation으로 남고, 100% 미만이면 job이 실패합니다.

| 조건 | 수정 전 (`74b3ead`) 정상 매칭 | 수정 후 (`8c57aac`~) 정상 매칭 | 수정 후 join→matched p50 / p95 | 채팅 p50 / p95 |
| --- | --- | --- | --- | --- |
| 1 프로세스, 1,000명 / 10초 분산 | 99.8 – 100% | **100%** (3회) | 2 / 4 ms | 1 / 8 ms |
| 4 프로세스, 2,000명 / 10초 분산 | 99.5% | **100%** (3회) | 2 / 4 ms | 2 / 4 ms |
| 1 프로세스, 1,000명 동시 | **4.6 – 42.8%** | **100%** (3회) | 210 / 598 ms | 468 / 716 ms |
| 4 프로세스, 2,000명 동시 | **31.6 – 84.9%** | **100%** (3회) | 423 / 525 ms | 500 / 672 ms |
| 1 프로세스, 1,000명 동시, 수신함 용량 50 (스트레스) | — | **100%** (2회) | 792 / 1,957 ms | 77 / 632 ms |

main 병합 후 다시 측정했을 때는 러너가 약 2배 느렸습니다(동시 1,000명 join→matched p50 561ms). 이때 스트레스 조건이 98%로 떨어졌고, 그 원인을 고친 뒤([T11](../troubleshooting.md#t11-한-프로세스에-1000명이-동시에-몰리면-매칭-알림이-유실됨) 2번 항목) [최종 실행](https://github.com/kimseoungyun/VideoChat/actions/runs/40171646156)에서는 모든 조건이 100%였습니다. 스트레스 조건에서는 2,000명분 중 채팅 메시지 1건이 재시도 끝에 버려졌습니다(매칭은 100%).

수정 전 실패는 channels_redis 수신함 초과(`ChannelFull`)로 생긴 매칭 알림 유실이었습니다. 원인 분석과 해결은 [트러블슈팅 T11](../troubleshooting.md#t11-한-프로세스에-1000명이-동시에-몰리면-매칭-알림이-유실됨)에 있습니다. 스트레스 조건의 지연이 큰 것은 backpressure로 전송을 기다린 시간입니다. 메시지를 버리는 대신 늦게 전달한 결과입니다.

실행 기록: [수정 전](https://github.com/kimseoungyun/VideoChat/actions/runs/40168907931) · [수정 후](https://github.com/kimseoungyun/VideoChat/actions/runs/40170066655)

```powershell
.\.runtime\redis\redis-server.exe --port 6380 --save '""' --appendonly no   # 별도 창
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\loadtest\bench.ps1 -Label mine -RedisUrl redis://127.0.0.1:6380/0          # 현재 구현 매트릭스 (3회 반복)
.venv\Scripts\python.exe loadtest\redis_cost.py --base http://127.0.0.1:8020 --redis redis://127.0.0.1:6380/0
```

원본 비교는 원본 트리를 꺼내 `loadtest\legacy.ps1 -App <경로>`로 실행합니다(Redis 6379 필요).
원본의 `asgi.py`는 Django 설정 전에 모델을 import하므로 Daphne로는 시작되지 않습니다. 그래서 원본 개발 방식대로 `manage.py runserver`를 사용합니다.

## 한계

- 영상/음성 미디어는 측정하지 않았습니다. 미디어는 브라우저끼리 WebRTC로 주고받으므로 서버 부하에 포함되지 않습니다. TURN 릴레이 용량은 별도 측정이 필요합니다.
- 노트북과 CI 러너처럼 클라이언트와 서버가 한 머신에 있는 결과입니다. 운영 용량을 산정하려면 실제 서버에서 클라이언트를 분리해 다시 측정해야 합니다.
- 부하 도구의 클라이언트는 하나의 IP(127.0.0.1)를 공유하므로, 측정 시에는 IP별 연결 제한을 환경변수로 해제했습니다(`loadtest/serve.ps1`).
