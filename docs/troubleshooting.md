# 트러블슈팅 기록

각 항목은 **증상 → 원인 → 해결 → 검증** 순서로 정리했습니다. T1–T5는 원본 구현(`c8d7002`)의 결함이고, T6–T12는 재구축 이후 측정과 테스트로 찾은 문제입니다.
원본 개발 당시 직접 해결한 문제 10가지는 [history/original-troubleshooting.txt](history/original-troubleshooting.txt)에 그대로 보존했습니다.

---

## T1. 아무도 없는 "유령 방"이 남아 이후 매칭을 망가뜨림

- **증상**: 원본에서 대화가 끝난 뒤에도 방이 `user_count=1`로 남았습니다. 이후 접속한 사람은 그 방으로 배정되어 혼자 기다렸습니다. 원본 개발 메모 9번에도 "유령 방" 문제가 기록돼 있고, 당시에는 `migrate` 때 Room을 전부 지우는 방식으로 우회했습니다.
- **원인**: 퇴장 처리가 `Room.objects.get()` → `user_count -= 1` → `save()`의 read-modify-write입니다. 두 사람이 동시에 나가면 둘 다 2를 읽고 1을 저장합니다(lost update).
- **해결**: 인원 카운터를 없앴습니다. 매칭 상태는 Redis Lua 스크립트 하나가 원자적으로 바꾸고, 참가자 상태에는 60초 TTL을 걸어 프로세스가 죽어도 저절로 정리되게 했습니다.
- **검증**: 원본은 20명 세션 후 유령 방 8–10개가 남았고, 다음 20명은 50–60%만 매칭됐습니다. 현재는 정리 작업 없이 연속 실행해도 매번 100% 매칭됩니다([부하 측정](benchmarks/README.md)).

## T2. 동시에 들어오면 세 명 이상이 한 방에 배정됨

- **증상**: 원본은 200명이 5초 안에 접속하면 정상 1:1 매칭이 3–22%였고, 한 방에 최대 15명이 들어갔습니다.
- **원인**: 방 선택(HTTP 뷰가 `user_count=1`인 방 조회)과 인원 증가(나중에 WebSocket 연결 시점)가 서로 다른 요청에서 일어납니다. 그 사이에 들어온 사람들이 모두 같은 방을 "한 자리 남은 방"으로 봅니다.
- **해결**: 클라이언트가 방을 고르지 않습니다. 서버가 `join` 하나를 받아 Lua 안에서 "대기자 꺼내기 + 양쪽에 같은 match_id 기록"을 한 번에 처리합니다.
- **검증**: 200개 동시 `join` 단위 테스트, 그리고 4개 프로세스에 나눠 붙인 800명 동시 접속에서 100% 정상 매칭(3회 반복).

## T3. 방 번호 충돌로 HTTP 500, 방이 꽉 차면 요청 스레드가 멈춤

- **증상**: 원본은 동시 접속 시 2–9건의 HTTP 500이 발생했습니다.
- **원인**: 새 방 번호를 `random.randint(1, 100)`으로 뽑고, 기존 번호와 겹치는지 확인한 뒤 `create()`합니다. 확인과 생성 사이에 다른 요청이 같은 번호를 쓰면 `UNIQUE constraint failed`가 납니다. 또 100개 방이 모두 존재하면 빈 번호를 찾는 `while True`가 끝나지 않습니다.
- **해결**: 방 번호 대신 `uuid4` match_id를 씁니다. 매칭 경로에서 SQL을 사용하지 않습니다.
- **검증**: 현재 구현의 모든 부하 실행에서 서버 오류 0건.

## T4. 다른 사람의 신호가 섞이고, 세 번째 사용자가 방을 깨뜨림

- **원인**: 원본은 방 그룹 전체에 `group_send`로 SDP/ICE를 보냈고, 입력 검증이 없었습니다. 방에 세 번째 사람이 들어오거나 이전 상대의 늦은 신호가 오면 연결이 엉켰습니다.
- **해결**: 서버가 지정한 상대에게만 1:1로 전달합니다. 모든 메시지는 현재 match_id와 일치해야 하고, 타입·크기·형식을 검증합니다(32 KiB 프레임, 초당 30개 토큰 버킷).
- **검증**: 이전 match_id 신호 폐기, 잘못된 JSON·미디어 값 거부, 다음 상대로 바꾼 뒤 늦게 온 메시지 미전달 테스트.

## T5. 원본은 운영용 ASGI 서버로 시작조차 되지 않음

- **증상**: 원본을 `daphne myproj.asgi:application`으로 실행하면 `ImproperlyConfigured: Requested setting INSTALLED_APPS`로 바로 종료됩니다.
- **원인**: `asgi.py`가 `DJANGO_SETTINGS_MODULE` 설정과 `get_asgi_application()` 호출 전에 모델을 쓰는 라우팅 모듈을 import합니다. 설정이 먼저 로드되는 `manage.py runserver`에서만 동작했습니다.
- **해결**: Django 앱을 먼저 초기화하고 라우팅을 import하도록 순서를 바꿨습니다. Dockerfile도 Daphne로 실행합니다.

## T6. 접속자마다 Redis 연결이 하나씩 생겨 서버가 종료됨

- **증상**: 부하 측정 중 500명 동시 접속에서 Daphne가 `ValueError: too many file descriptors in select()`로 종료되고, 이후 모든 연결이 거부됐습니다.
- **원인 분석**: Windows의 `select()` 한도(512)는 환경 요인입니다. 하지만 `INFO clients`로 확인하니 **WebSocket 200개에 Redis 연결이 212개**였습니다. `Matchmaker`가 WebSocket마다 `Redis.from_url()`로 별도 연결 풀을 만들어, 접속자 1명이 소켓 2개를 쓰고 있었습니다. 이 구조는 Linux에서도 Redis `maxclients`와 연결 생성 비용 문제로 이어집니다.
- **해결**: 이벤트 루프당 하나, 상한 50의 `BlockingConnectionPool`을 공유합니다(`chat/matchmaking.py`의 `shared_redis()`). 헬스 체크도 같은 풀을 씁니다.
- **검증**: 같은 시나리오에서 Redis 연결 212 → **17**. Windows에서는 프로세스당 접속 수를 낮추고 프로세스를 늘려 1,000명까지 측정했습니다.

## T7. 부하 측정 결과가 틀렸던 문제 (측정 도구의 버그)

- **증상**: 동시 접속을 연속으로 반복하면 세 번째 실행에서 채팅 수신 타임아웃이 21건, 78건 발생했고, 반복할수록 지연이 커졌습니다.
- **처음 가설**: channels_redis의 프로세스 공유 수신함 용량(`capacity: 200`) 초과(`ChannelFull`). 하지만 서버 로그에 예외가 없어 기각했습니다. 이 규모(프로세스당 200명)에서는 기각이 맞았지만, 같은 가설이 더 큰 규모에서 실제 원인이 됐습니다([T11](#t11-한-프로세스에-1000명이-동시에-몰리면-매칭-알림이-유실됨)).
- **원인**: 측정 도구가 "모든 클라이언트 매칭 완료" 후 0.5초 만에 소켓을 닫았습니다. 버스트에서는 채팅 중계가 그보다 늦게 끝나는데, 보낸 쪽이 먼저 나가면 서버는 **끝난 매칭의 메시지를 정상적으로 폐기**합니다. 서버가 아니라 도구의 문제였습니다.
- **해결**: 수신 측까지 끝난 뒤 해제하고, 실패를 connect/match/chat 단계별로 기록합니다. 실행 사이에는 5초 간격을 두어 이전 실행의 종료 처리가 다음 측정에 섞이지 않게 했습니다.
- **배운 점**: 오류율보다 먼저 측정 도구를 의심하고, 실패를 단계별로 분리해 기록해야 원인을 좁힐 수 있습니다.

## T8. 메시지 하나를 중계할 때마다 Redis 명령 26개

- **측정**: `INFO commandstats`로 확인하니 채팅 1개당 명령이 26개였습니다. 보내는 쪽과 받는 쪽 consumer가 각각 매칭 Lua(`state`)를 실행해 "아직 이 상대와 매칭 중인가"를 Redis에서 다시 읽고 있었습니다.
- **해결**: 상대 채널과 match_id는 매칭 확정 이벤트(`pair_ready`)에서 Redis로 한 번 검증한 뒤 consumer에 보관합니다. 중계는 로컬 값으로 확인합니다. 상대가 이미 다른 매칭으로 넘어갔다면 받는 쪽의 match_id가 달라서 폐기됩니다. 따라서 안전성은 같고, 늦게 도착한 메시지가 새 상대에게 전달되는 일은 없습니다.
- **검증**: 26 → **10개**(-62%), 매칭 Lua 0회. 같은 측정을 변경 전 코드로도 실행해 비교했습니다. "다음 상대 이후 이전 match_id 메시지 미전달" 테스트를 추가했습니다.

## T9. 같은 공유기 사용자끼리 신고하면 그 IP 전체가 매칭 불가

- **증상**: 신고 기능을 넣은 뒤 브라우저 테스트를 다시 실행하자, 처음에는 통과하던 매칭 테스트가 모두 "상대를 찾는 중"에서 멈췄습니다.
- **원인**: 게스트 신원은 해시한 IP입니다. 테스트의 모든 브라우저가 127.0.0.1이라 신고자와 대상의 신원이 같았고, 신고 시 `blocks:<신원>`에 **자기 자신**이 추가됐습니다. 실제 서비스에서는 같은 학교·회사·통신사 NAT의 사용자 한 명이 신고하면 그 IP 전체가 서로 매칭되지 않는 버그입니다.
- **해결**: 신고자와 대상의 신원이 같으면 신원 단위 차단과 신고 누적을 적용하지 않습니다. 대신 연결 단위 제외만 남깁니다(신고 기록은 저장).
- **검증**: "같은 IP 게스트 간 신고 후에도 같은 IP의 다른 사용자끼리 매칭" 서버 테스트, 신고 e2e를 연속 실행해도 기존 e2e가 통과하는지 확인.

## T10. 상대가 먼저 나간 뒤 "다음 상대"를 누르면 같은 사람과 다시 매칭될 수 있음

- **원인**: `leave`는 직전 상대를 `blocked`로 남기도록 설계됐지만, 이미 상대가 없는 상태에서 다시 `leave`하면(신고/종료 후 next) 키를 지우면서 `blocked`도 사라졌습니다. 양쪽이 모두 그렇게 하면 방금 헤어진 두 사람이 다시 매칭됩니다.
- **해결**: 현재 상대가 없으면 기존 `blocked` 값을 유지합니다.
- **검증**: 회귀 테스트가 **수정 전 Lua에서는 실패하고 수정 후 통과**하는 것을 확인했습니다. 신고 e2e에서 신고한 두 사람이 모두 "다음 상대"를 눌러도 다시 연결되지 않습니다.

## T11. 한 프로세스에 1,000명이 동시에 몰리면 매칭 알림이 유실됨

- **증상**: Windows에서는 프로세스당 200명까지만 측정할 수 있었습니다. 그래서 GitHub Actions의 Linux 러너에서 부하 측정을 돌렸습니다. 1,000명이 10초에 걸쳐 오면 99.8–100%였지만, **한 순간에 몰리면 정상 매칭이 5–43%**에 그쳤습니다. 실패는 모두 `ready`를 받은 뒤 매칭 단계에서 났고, "서버가 연결을 끊음"과 "타임아웃" 수가 매번 **정확히 같았습니다**. 한 쌍에서 한쪽은 끊기고 다른 쪽은 알림을 못 받았다는 뜻입니다.
- **기각한 가설**: Redis 연결 풀 고갈(상한 50, 대기 3초). 풀을 4로 줄여도 200명 동시 접속이 100% 성공해 기각했습니다.
- **원인**: channels_redis는 **한 프로세스의 모든 소켓이 수신함 하나를 공유**하고, `capacity`(200)가 그 수신함 전체에 적용됩니다. 500쌍의 `pair.ready`가 한꺼번에 쌓이면 초과분 `send()`가 `ChannelFull`을 던지고, 처리되지 않은 예외로 consumer가 종료됩니다(close 1011). 그 쌍의 상대는 Redis상으로는 매칭됐지만 알림을 받지 못해 영원히 기다립니다. 부하 도구가 close code를 기록하게 고친 뒤, 용량을 20으로 줄여 로컬에서 **같은 패턴을 재현**했습니다(정상 매칭 24%, `ChannelFull` 79건, 끊김 76 = 타임아웃 76).
- **해결**
  1. 모든 channel layer 전송을 `deliver()`로 통일했습니다. `ChannelFull`이면 0.05초부터 두 배씩 늘려 최대 약 3초까지 재시도합니다(backpressure). 수신함은 수 밀리초 단위로 비워지므로 버스트를 흡수합니다.
  2. 그래도 `pair.ready`를 전하지 못하면 매칭을 되돌립니다. 한쪽만 아는 매칭이 남지 않습니다. 처음에는 두 사람을 모두 대기열로 돌려보냈는데(`unpair`), main 병합 후 CI에서 수신함 50 스트레스 조건이 98%로 실패했습니다. 매칭은 누군가 `join`할 때만 일어나므로, 새 사용자가 오지 않으면 되돌려진 두 사람이 계속 기다린 것입니다. 지금은 상대만 대기열로 돌려놓고(`release`) 자신이 곧바로 다시 매칭을 시도하며, 3번 실패한 뒤에만 둘 다 대기열로 돌아갑니다. 전달 실패를 강제로 주입한 consumer 테스트로 이 경로를 검증했습니다(재시도를 끄면 실패함).
  3. 기본 용량을 소켓 수에 맞춰 5,000으로 올렸습니다(`CHANNEL_CAPACITY`). 메시지는 30초 후 만료됩니다.
  4. 재시도 후에도 버린 메시지는 `videochat_channel_full_dropped_total`로 집계합니다.
- **검증**: 용량 20 재현 조건에서 3회 모두 100%, 예외 0건. `unpair` 단위 테스트. Linux CI에서 기본 설정과 용량 50 스트레스 조건을 측정합니다([부하 측정](benchmarks/README.md#결과-4--linux-ci-측정)).
- **배운 점**: 측정할 수 있는 규모를 환경이 제한하면 그 한계 너머의 병목은 보이지 않습니다. T7에서 기각한 가설도 "이 규모에서는 아니다"였지, "원인이 아니다"는 아니었습니다.

## T12. 원인과 다른 안내 문구 (Firefox 검증 중 발견)

- **증상**: 카메라를 열지 못하면 오류 종류와 관계없이 "HTTPS 또는 localhost에서 접속해 주세요"가 표시됐습니다. localhost에서 `AbortError`가 난 사용자에게는 틀린 안내입니다.
- **해결**: 보안 컨텍스트가 아닐 때만 HTTPS 안내를 보여 줍니다. `AbortError`, `OverconstrainedError`에는 각각 맞는 안내를 추가하고, 나머지는 장치와 권한을 확인하라고 안내합니다.
